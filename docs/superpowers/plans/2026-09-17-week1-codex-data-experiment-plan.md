## 3. 数据接入路径

第一步使用明确任务文件的只读回放：Codex transcript → 可见消息规范化 → 本地案例。它提供首批真实数据，不依赖先完成双向工具集成。

后续若手动刷新成为负担，再采用 Hooks 提供的事件和 transcript 路径做增量通知。官方说明 Hooks 可接收 `session_id`、`transcript_path`、`cwd`；同时明确 transcript 格式不是稳定接口。适配器必须识别版本和未知结构，不能静默产生“成功但零消息”。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

本周不把完整插件、后台常驻服务、MCP 双向调用或全量历史收集列为前置条件。持续采集与把学习结果回传给 Codex 是后续两个独立工作项。

## 4. 最小数据约定

| 信息 | 本周处理要求 |
| --- | --- |
| 身份与顺序 | 保留任务 ID、消息 ID、回合 ID、角色、源行号和文件来源 |
| 时间 | 优先保留消息创建时间，同时保留写入时间；字段缺失明确标记，不能补成当前时间。已观察到助手创建时间缺失、写入时间有效时标 warning；用户创建时间缺失或无效时间标 error |
| 用户内容 | 当前格式依据 `content_item_kinds` 区分 `user.*` 与环境／插件说明；未知格式进入质量报告 |
| 用户选项回复 | 展开结构化问题及答案，同时保留原始载体，不能丢掉“每周 3–5 小时”等信号 |
| 助手回复 | 区分 commentary 与 final_answer；作为助手表达，不当作人的事实或认可 |
| 非对话材料 | 排除内部 reasoning、开发者指令、原始工具参数和大段工具输出；工具结果需求另行设计 |
| 重复与尾部 | 规范来源选 `response_item/message`；相同消息 ID 重读不增加；未写完的最后一行可等待下次刷新，已完成行损坏必须报告 |
| 来源与变更 | 保留快照字节边界和校验值；同 ID 内容变化时报告修订，不能把它当成新独立证据 |
| 覆盖 | 报告保留数、按原因排除数、未知类型、缺失字段与损坏行；零条输出必须解释 |

初期只读当前任务。扩大到其他任务时逐个明确任务白名单，不因为项目名称相似就纳入。用于选择提醒时段的其他任务只读取了用户事件时间和来源类型，没有把其正文加入实验样本。

后续范围更新（2026-09-17）：用户要求从计算机历史记录报告发现侧写信息，已手工读取选定的 11 份 Computer History 报告及必要原始事件。它们是独立标注来源的开发材料，不改变本节 Codex 读取器的单任务范围。同一事件在 Codex、历史摘要和屏幕记录中的多个载体按同一组处理；摘要内容本身不等于用户认可。

### D. 普通记忆基线

采用同一基座模型加简单历史检索，记录当前任务目标、协作者相关信息、未知和建议下一步。输出先保存，后续反馈再用于核对。

基线必须在不携带本次完整讨论的独立上下文中运行；当前助手已看到后续答案，其直接回答不能作为盲测结果。优先使用已有环境内的可隔离运行方式，记录模型、提示、输入截止点和调用预算；不以新增付费服务作为首轮前提。

当前任务的所有已看内容用于开发；独立效果评估需要新发生的事件或另一个明确选定的任务。缺少独立样本时，只报告“回放机制可用”，不报告持续学习已有效。

2026-09-17 已完成：gpt-6-astra、low 推理强度下 7 次独立上下文回放，保留冻结输入、提示、输出、运行配置与用量。4 个真实案例满足全部检查，2 个有覆盖缺口；这些结果只用于开发。另有 1 次环境探测与 review 后 2 次补充情境回放，分别记账；后者不能算作独立留出验证。报告见本地 `reports/experiments/week-01/baseline-2026-09-17/report.md`。

## 6. 第一周完成条件

1. 一个明确任务能被可重复读取，原文件不被修改，来源可定位。
2. 过滤、去重、结构化回复与损坏输入有验证，未知内容不会静默当作事实。
3. 首批案例保留情境和后续反馈的时间边界，真实与合成材料分开。
4. 至少说明基线是否跑通、哪些效果尚不能判断；不足之处明确接续。
5. Review 完成，推进记录和下一步已更新。

只有满足这些条件才推进动态侧写实验。根据时间预算允许拆为两个周迭代，不因提醒触发而自动标为完成。

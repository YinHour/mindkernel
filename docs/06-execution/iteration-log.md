## 固定流程

每个工作单元建议 30–90 分钟，同一周可有多个工作单元，但只有一个当前工作项。

### 1. 推进前：写清本次要得到什么

- 阅读当前工作项和上次 review；核对文件与记录一致。
- 写下本次唯一交付、投入上限和怎样判断完成。
- 新要求改变优先级时更新记录，保留改变原因；不沿用已过时的限制。

### 2. 推进：保留证据

- 在范围内完成一个小交付，记录输入、产物和验证路径。
- 到时间上限仍未完成时保存中间状态和下一步。
- 新问题若不阻塞当前目标，进入候选项；阻塞则明确它如何影响交付。

### 3. Review：结束前必须判断

| 检查 | 需要回答的问题 |
| --- | --- |
| 目标 | 本次交付是否回答了原问题？用户的新要求是否已纳入？ |
| 证据 | 文件、结果与实际执行是否支持完成声明？ |
| 质量 | 是否检查了本次变化最可能失败的边界？ |
| 成本 | 是否增加额外教学、维护或调用负担？未知用时不补造 |
| 剩余问题 | 什么还未解决，影响本项还是后续工作？ |

结论只取：通过／需修正／证据不足。技术 review 可由开发助手完成；个人意图与协作价值需要协作者的真实反馈。

### 4. 更新：形成下一次可接续的入口

- 将实际完成、证据路径和 review 结论写入下方工作记录。
- 修改顶部当前项状态，指定下一次 15–30 分钟动作。
- 状态或瓶颈变化时更新瓶颈记录；新技术必须对应具体瓶颈和最小验证，保留旧结论及适用条件。
- 只有通过 review 且记录更新完成，才把该工作项标记为完成。
- 目标或方法发生变化时，只更新受影响计划；避免在多个文件重复维护详细进度。
- 对用户说明结果、验证和下一步。Git 提交／推送若未执行，单独说明。

### 暂停与恢复

- 暂停时记录原因、已完成部分、恢复条件和最小下一步。
- 若此前意外中断，没有收尾记录，下一次先核对工作区和可见产物，再补记“恢复核对”，不猜测完成情况。
- 连续两个周检查点仍无进展时，将当前项缩小为一个 15–30 分钟恢复动作；不自动新增计划或要求补齐落后的周数。
- 用户提到的“两次中断”作为已知经历保留；其具体原因尚未查明，不归因于某种工作习惯。
